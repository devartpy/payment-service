# Асинхронный сервис процессинга платежей

## Описание

Необходимо реализовать микросервис для асинхронной обработки платежей. Сервис
принимает запросы на оплату, обрабатывает их через внешний платежный шлюз
(эмуляцию) и уведомляет клиента о результате через webhook.

Это требования к микросервису. Реализованы POST/GET платежей, проверка `X-API-Key`, защита от последовательного повторного использования `Idempotency-Key`, атомарная запись платежа с outbox, отдельный RabbitMQ publisher, consumer, эмулятор шлюза и webhook. Фактический HTTP-контракт описан в [REST API](api.md), последовательность — на [диаграмме](architecture/diagrams/payment-processing-sequence.puml).

## Сущности

### Платеж (Payment)
- ID платежа (уникальный идентификатор)
- Сумма (decimal)
- Валюта (RUB, USD, EUR)
- Описание (строка)
- Метаданные (JSON поле для дополнительной информации)
- Статус (`pending`, `succeeded`, `failed`); `succeeded` и `failed` — конечные статусы
- Idempotency key (уникальный ключ для защиты от дублей)
- Webhook URL (для уведомления о результате)
- Даты создания и обработки

## Функционал API

### Создание платежа

1. POST /api/v1/payments
- Заголовки: `X-API-Key` и `Idempotency-Key` (оба обязательны)
- Body: сумма, валюта, описание, метаданные, webhook_url
- Ответ: 202 Accepted, payment_id, статус, created_at

2. GET /api/v1/payments/{payment_id}
- Заголовок: `X-API-Key` (обязателен)
- Ответ: детальная информация о платеже

## Брокер сообщений

1. API создаёт `Payment(PENDING)` и OutboxEvent в одной транзакции. Один экземпляр publisher читает все события через `SELECT ... ORDER BY created_at` без блокировки, публикует каждое в `payments.new` и ждёт положительного подтверждения RabbitMQ и успешной маршрутизации. После каждого подтверждения удаляет соответствующий OutboxEvent и отдельно фиксирует транзакцию БД; статус Payment при публикации не меняется. При отсутствии подтверждения или сбое фиксации запись остаётся для повторной публикации. Consumer создаёт топологию RabbitMQ, Compose запускает publisher после готовности consumer.
2. Один consumer:

    2.1 Получает сообщение из `payments.new` и читает платёж из БД. Если статус конечный, пропускает шлюз и переходит к webhook.

    2.2 При `PENDING` эмулирует обработку платежа (случайная задержка 2–5 сек, 90% успех, 10% ошибка для каждого вызова).

    2.3 Обновляет статус в БД

    2.4 Отправляет webhook уведомление на указанный URL

    2.5 Подтверждает исходное сообщение при HTTP `200` от мерчанта. Для сбоя сети, таймаута или `5xx` повторяет отправку webhook до трёх попыток всего с экспоненциальной задержкой. При `4xx` сразу отклоняет исходное сообщение без возврата в очередь; после третьей неудачной попытки также отклоняет его. Настроенный dead-letter exchange (DLX) переносит исходное сообщение в `payments.dead_letter`. Текущий второй подписчик логирует это сообщение и подтверждает его, после чего RabbitMQ удаляет сообщение из DLQ.

## Гарантии доставки

1. Outbox pattern для гарантированной публикации событий
2. Idempotency key для защиты от дублей
3. Dead Letter Queue (DLQ) для исходного сообщения при `4xx` webhook либо после трёх ошибок сети, таймаута или `5xx`. Ошибка webhook не меняет конечный статус платежа. Статус `failed` сам по себе не служит причиной отправки в DLQ: о нём также отправляется webhook.

При повторной доставке RabbitMQ consumer не вызывает шлюз для конечного статуса. Если consumer упал после вызова эмулятора, но до сохранения статуса, следующий вызов может получить другой случайный результат. При подключении реального банковского шлюза его адаптер передаёт `payment.idempotency_key`, а идемпотентность повторных вызовов обеспечивает сам шлюз. Текущий лимит в три отправки webhook действует в рамках одного запуска обработчика; после перезапуска счётчик начинается заново. Для глобального лимита нужно хранить счётчик вне памяти процесса. Webhook может прийти мерчанту повторно, если consumer упал после HTTP `200`, но до подтверждения сообщения RabbitMQ.

## Аутентификация
Статический API ключ в заголовке `X-API-Key` для всех эндпоинтов

## Стек технологий

- FastAPI + Pydantic v2
- SQLAlchemy 2.0 (асинхронный режим)
- PostgreSQL
- RabbitMQ (FastStream)
- Alembic (миграции)
- Docker + docker-compose

## Требования к результату
1. Модели и миграции: таблицы payments и outbox
2. API эндпоинты: создание и получение платежа
3. Consumer: один обработчик, делающий всё
4. Outbox pattern: гарантированная доставка событий
5. Retry отправки webhook: до трёх попыток с экспоненциальной задержкой при сбое сети, таймауте или `5xx`; остальные шаги не входят в этот retry.
6. Dead Letter Queue: исходное сообщение при `4xx` webhook или после исчерпания трёх попыток; повторный разбор не запускает платёж заново
7. Docker: compose файл с postgres, rabbitmq, api, consumer и publisher
8. Документация: README с запуском и примерами

## Критерии оценки
- Архитектура и чистота кода
- Корректная реализация Outbox pattern
- Работа с RabbitMQ (очереди, обменники, DLQ)
- Идемпотентность
- Обработка ошибок и retry логика
- Работоспособность Docker-окружения
