# Асинхронный сервис процессинга платежей

## Описание

Необходимо реализовать микросервис для асинхронной обработки платежей. Сервис
принимает запросы на оплату, обрабатывает их через внешний платежный шлюз
(эмуляцию) и уведомляет клиента о результате через webhook.

Это требования к новому микросервису. Текущая реализация содержит HTTP-каркас и инфраструктурную основу; платёжные эндпоинты, модели, очереди и consumer ещё предстоит добавить. Структура кода начинается в [README](../README.md), целевая последовательность показана на [диаграмме](architecture/diagrams/payment-processing-sequence.puml).

## Сущности

### Платеж (Payment)
- ID платежа (уникальный идентификатор)
- Сумма (decimal)
- Валюта (RUB, USD, EUR)
- Описание (строка)
- Метаданные (JSON поле для дополнительной информации)
- Статус (pending, succeeded, failed)
- Idempotency key (уникальный ключ для защиты от дублей)
- Webhook URL (для уведомления о результате)
- Даты создания и обработки

## Функционал API

### Создание платежа

1. POST /api/v1/payments
- Заголовки: `X-API-Key` и `Idempotency-Key` (оба обязательны)
- Body: сумма, валюта, описание, метаданные, webhook_url
- Ответ: 202 Accepted, payment_id, статус, created_at

2. GET /api/v1/payments/{payment_id}
- Ответ: детальная информация о платеже

## Брокер сообщений

1. При создании платежа запись события сохраняется в outbox в одной транзакции с платежом. Отдельный компонент-публикатор доставляет событие в очередь `payments.new` через RabbitMQ и отмечает запись опубликованной только после подтверждения брокера. Под «отдельным компонентом» понимается отдельная роль в коде; способ её развёртывания пока не задан.
2. Один consumer:

    2.1 Получает сообщение из очереди

    2.2 Эмулирует обработку платежа (2-5 сек, 90% успех, 10% ошибка)

    2.3 Обновляет статус в БД

    2.4 Отправляет webhook уведомление на указанный URL

    2.5 Реализует повторные попытки при ошибках отправки webhook

## Гарантии доставки

1. Outbox pattern для гарантированной публикации событий
2. Idempotency key для защиты от дублей
3. Dead Letter Queue (DLQ) для сообщений, не обработанных после 3 попыток. Эта политика обработки сообщений отличается от повторных попыток отправки webhook.

## Аутентификация
Статический API ключ в заголовке `X-API-Key` для всех эндпоинтов

## Стек технологий

- FastAPI + Pydantic v2
- SQLAlchemy 2.0 (асинхронный режим)
- PostgreSQL
- RabbitMQ (FastStream)
- Alembic (миграции)
- Docker + docker-compose

## Требования к результату
1. Модели и миграции: таблицы payments и outbox
2. API эндпоинты: создание и получение платежа
3. Consumer: один обработчик, делающий всё
4. Outbox pattern: гарантированная доставка событий
5. Retry отправки webhook: 3 попытки с экспоненциальной задержкой; требование не относится к публикации outbox и всем шагам обработки consumer.
6. Dead Letter Queue: для окончательно упавших сообщений
7. Docker: compose файл с postgres, rabbitmq, api, consumer
8. Документация: README с запуском и примерами

## Критерии оценки
- Архитектура и чистота кода
- Корректная реализация Outbox pattern
- Работа с RabbitMQ (очереди, обменники, DLQ)
- Идемпотентность
- Обработка ошибок и retry логика
- Работоспособность Docker-окружения
