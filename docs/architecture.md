# Архитектура сервиса

Шаблон задаёт границы одного развёртываемого сервиса. Внутри него используется модульная структура с правилами DDD: предметная область разделена на модули, а в каждом модуле отделены домен, сценарии, инфраструктура и HTTP API. `src/modules/payment/` — каркас для будущего бизнес-модуля; его реализация, миграции и предметные тесты добавляются в новом сервисе.

Требования к платёжному процессу находятся в [задании](project.md), а его целевая [диаграмма последовательности](architecture/diagrams/payment-processing-sequence.puml) — в каталоге диаграмм. Они описывают будущее поведение: сейчас `src/api/main_router.py` не содержит маршрутов платежей.

Такой выбор позволяет расширять один сервис несколькими модулями, сохраняя явные зависимости. Модуль внутри `src/modules/` сам по себе не является отдельным микросервисом: все модули этого репозитория запускаются и развёртываются вместе.

## Структура проекта

```text
src/
├── api/
│   ├── app.py             # Фабрика FastAPI
│   ├── main.py            # Точка входа Uvicorn
│   ├── main_router.py     # Подключение маршрутов модулей
│   ├── middlewares.py     # HTTP trace_id
│   └── dependencies.py    # Зависимости HTTP-слоя (каркас)
├── common/
│   ├── configs/           # Настройки БД, FastAPI и логов
│   ├── infrastructure/
│   │   ├── base.py        # Base, BaseModel и общие метаданные ORM
│   │   ├── database.py    # Фабрики движка и сессий
│   │   ├── sqlalchemy_uow.py # Общий жизненный цикл SQLAlchemy UoW
│   │   └── model_registry.py # Поиск моделей бизнес-модулей
│   ├── unit_of_work.py    # Общий контракт транзакции без SQLAlchemy
│   └── logger.py          # Настройка логирования
└── modules/
    └── payment/           # Переименовывается под предметную область
        ├── domain/
        │   ├── models.py         # Сущности и агрегаты
        │   ├── value_objects.py  # Объекты значений и перечисления
        │   └── exceptions.py     # Доменные ошибки
        ├── application/
        │   ├── use_cases.py      # Сценарии приложения
        │   ├── interfaces.py     # Контракты репозиториев, UoW и сервисов
        │   └── dtos.py           # Данные сценариев, если нужны
        ├── infrastructure/
        │   ├── db/
        │   │   ├── models.py
        │   │   └── mappers.py
        │   ├── repositories.py
        │   └── unit_of_work.py
        └── api/v1/
            ├── router.py
            └── schemas.py
```

`src` остаётся именем Python-пакета этого сервиса. Новые предметные области получают отдельные каталоги рядом с `payment`, каждый с той же структурой.

## Слои модуля

| Каталог | Ответственность | Зависимости |
| --- | --- | --- |
| `domain/` | Сущности, объекты значений, инварианты, доменные ошибки | Стандартная библиотека и собственный домен |
| `application/` | Сценарии, команды и результаты, контракты репозиториев и Unit of Work | Собственный `domain/` |
| `infrastructure/` | SQLAlchemy-модели, мапперы, репозитории, реализация Unit of Work и внешние адаптеры | `application/`, `domain/`, библиотеки инфраструктуры |
| `api/v1/` | HTTP-маршруты, валидация запроса и преобразование результата в ответ | `application/`, FastAPI и Pydantic |

Доменные объекты не зависят от FastAPI, Pydantic и SQLAlchemy. `domain/models.py` содержит бизнес-сущности, а ORM-модели остаются в `infrastructure/db/models.py`; между ними работают мапперы. Доменные ошибки определяются в `domain/exceptions.py` и преобразуются в HTTP-ответы на границе API.

Версии HTTP-контракта принадлежат `api/`: схемы запросов и ответов для v1 находятся в `api/v1/schemas.py`. При появлении v2 добавьте `api/v2/router.py` и `api/v2/schemas.py`. `application/dtos.py` предназначен только для независимых от транспорта команд и результатов сценариев, когда простых аргументов и доменных объектов недостаточно. Эти данные не версионируются вместе с HTTP-маршрутами и не импортируют схемы из `api/`. По мере роста модуля файлы `use_cases.py`, `interfaces.py` и `dtos.py` можно разделить на пакеты по сценариям.

Направление зависимостей внутри модуля: `api → application → domain` и `infrastructure → application/domain`. Контракты репозиториев и Unit of Work принадлежат `application/`; инфраструктура реализует эти контракты. `application/` не импортирует `infrastructure/`, а `domain/` не импортирует остальные слои.

`src/api/` служит внешней границей сервиса. Здесь допустимы импорты всех слоёв для связывания контрактов с реализациями. Бизнес-правила в этом каталоге не размещаются.

`src/common/` содержит только технические компоненты, действительно общие для нескольких модулей: настройки, логирование и фабрики инфраструктуры. Бизнес-сущности одного модуля не переносятся в `common/` ради повторного использования. Другой модуль взаимодействует с ним через явно предоставленный контракт, а не через его ORM-модели или внутренний репозиторий.

При взаимодействии модулей вызывающий модуль зависит от опубликованного контракта другого модуля. Связывание контракта с реализацией выполняется на внешней границе сервиса, например в `src/api/`; прямые импорты внутренних ORM-моделей между модулями не допускаются. Если потребуется отдельное развёртывание, границу сервиса и контракт обмена определяют отдельно.

## Сборка и запуск HTTP-приложения

`create_app()` в `src/api/app.py` создаёт FastAPI, применяет настройки документации и CORS, затем подключает `main_router`. При пустом `FA_CORS_ORIGINS` CORS middleware не добавляется; при `FA_ENABLE_DOCS=false` отключаются OpenAPI, Swagger UI и ReDoc. Файл `main_router.py` пока содержит пустой `APIRouter`: маршруты подключаются при реализации модулей.

Точка входа `src/api/main.py` уже содержит сборку процесса:

```python
setup_logger(service_name="api")
app = TraceIdMiddleware(create_app())
```

Запуск из корня проекта после установки зависимостей: `uv run --locked uvicorn src.api.main:app --reload`. Внешняя обёртка `TraceIdMiddleware` охватывает также ответы 500, которые создаёт FastAPI. `app.py` не настраивает логирование, поэтому `create_app()` можно вызывать отдельно при проверке HTTP-настроек. Соединение с PostgreSQL и миграции пока не подключены к запуску API.

## Конфигурация

`src/common/configs/` разделяет настройки по назначению: `DatabaseConfig` для PostgreSQL, `FastAPIConfig` для HTTP-приложения и `LoggerConfig` для логирования. Все они наследуют `CommonConfig` с общими правилами чтения окружения. Переменные окружения имеют приоритет над локальным `.env`. Относительный путь `.env` вычисляется от текущего рабочего каталога процесса, поэтому команды запускаются из корня проекта либо получают окружение извне.

Импорт `src.common.configs` не читает окружение и не создаёт объекты настроек. Публичный интерфейс пакета — `get_db_config()`, `get_fastapi_config()` и `get_logger_config()`. Каждая функция создаёт объект при первом вызове и затем возвращает его из кеша. В тестах класс можно импортировать из соответствующего файла и создать с нужными значениями; для повторного чтения окружения очистите кеш соответствующей функции.

`DatabaseConfig.async_url` возвращает объект SQLAlchemy `URL`. `create_engine()` в `src/common/infrastructure/database.py` создаёт движок только при вызове и передаёт ему этот объект напрямую: специальные символы в пароле не нужно экранировать вручную. `create_session_factory(engine)` создаёт фабрику сессий; владелец процесса закрывает движок при завершении через `await engine.dispose()`. Не записывайте URL с открытым паролем в логи. Значение `FA_CORS_ORIGINS` для списка адресов задаётся JSON-массивом, например `FA_CORS_ORIGINS='["http://localhost:3000"]'`.

## Логирование

Каждый процесс API или воркера вызывает `setup_logger(service_name="api")` в своей точке запуска, передавая своё имя (`api`, `scheduler`, `consumer` и т. д.). Импорт `src.common.logger` не настраивает logging. Повторный вызов `setup_logger()` заменяет обработчик root, не создавая дублирующихся строк. Настройка управляет корневым обработчиком процесса и направляет записи стандартного `logging`, `structlog` и Uvicorn в stdout.

JSON включён по умолчанию (`APP_JSON_LOGS=true`); для читаемого вывода в терминале установите `APP_JSON_LOGS=false`. `APP_LOG_LEVEL` по умолчанию равен `INFO`. Полный перечень настроек приведён в [Environment Variables](environment-variables.md). Сервис сохраняет одну JSON-запись на строку и не отправляет логи напрямую в систему их сбора.

Контракт JSON-записи:

| Поле | Содержание |
| --- | --- |
| `timestamp` | Время события в ISO 8601, UTC |
| `level` | Уровень строчными буквами, например `info` |
| `event` | Краткое имя или описание события |
| `logger` | Имя логгера или модуля |
| `service` | Имя, переданное в `setup_logger(service_name=...)` |
| `trace_id` | Идентификатор трассы, если он привязан к контексту |
| `exception` | Структурированный traceback при записи исключения; локальные переменные в него не включаются |

Дополнительные поля событий задаются именованными аргументами, например `structlog.get_logger(__name__).info("order_created", order_id=order_id)`. Имя `event` и общие поля контракта не используются для бизнес-атрибутов. В логи не передаются пароли, токены и другие секреты.

`TraceIdMiddleware` читает заголовок из константы `X_TRACE_ID_HEADER` в `src/api/middlewares.py` или создаёт ID через `get_default_trace_id()`. ID привязывается к контексту запроса и возвращается в заголовке с тем же именем. Значение константы в шаблоне — `X-Trace-ID`; при создании сервиса замените его на имя заголовка, согласованное с вызывающей системой. Входящий ID используется как есть, согласно этому контракту. Для фоновых задач контекст создаётся отдельно.

## Транзакция и Unit of Work

Общий `AbstractUnitOfWork` находится в `src/common/unit_of_work.py` и не импортирует SQLAlchemy. Контракт конкретного модуля в `application/interfaces.py` может расширять его свойствами своих репозиториев. `SQLAlchemyBaseUnitOfWork` в `src/common/infrastructure/sqlalchemy_uow.py` реализует общий контракт: создаёт сессию при входе в `async with`, откатывает транзакцию при исключении и всегда закрывает сессию. Без явного `commit()` незавершённая транзакция откатывается при закрытии сессии. Реализация UoW конкретного модуля в `infrastructure/unit_of_work.py` наследует SQLAlchemy-базу и при наличии отдельного контракта модуля реализует также его; репозитории создаются на основе `self.session`. Один сценарий определяет границу транзакции и использует нужные репозитории в рамках одного UoW. Репозитории не вызывают `commit()` самостоятельно.

Для каждой операции создаётся отдельная `AsyncSession`. Одну сессию нельзя одновременно использовать в нескольких асинхронных задачах. HTTP-слой передаёт сценарию UoW или его фабрику через зависимости; сценарий не импортирует FastAPI.

## Данные и интеграции

Каждый развёртываемый сервис владеет своими данными. Пока модули работают в одной базе сервиса, у неё один набор миграций Alembic. Все ORM-модели наследуют `Base` или `BaseModel` из `src/common/infrastructure/base.py`. Функция `load_models()` находит и импортирует `src/modules/<имя>/infrastructure/db/models.py` для каждого модуля; `alembic/env.py` вызывает её до чтения `Base.metadata`. Если в модуле есть каталог `db/`, но нет `models.py`, загрузка завершается ошибкой. Если зарегистрированных таблиц пока нет, autogenerate также завершается ошибкой вместо генерации удаления таблиц.

Alembic использует переменные `DB_*` из `.env` или окружения процесса и создаёт отдельный движок на время миграции. После добавления моделей и запуска PostgreSQL создайте ревизию из корня проекта:

```powershell
uv run --locked alembic revision --autogenerate -m "create_tables"
```

Команда требует работающей базы для сравнения схем. `alembic.ini` запускает `ruff check --fix`, затем `ruff format` для нового файла ревизии; поэтому Alembic запускают из окружения с установленной группой `dev`. Автоформатирование не проверяет смысл изменений: прочитайте `upgrade()` и `downgrade()`, особенно операции удаления таблиц или колонок. После проверки примените ревизию командой `uv run --locked alembic upgrade head`. Миграции выполняются как отдельный шаг развёртывания, а не каждой репликой API при старте.

FastStream с поддержкой RabbitMQ уже входит в основные зависимости `pyproject.toml`, но адаптер, конфигурация брокера и его сервис в Compose пока отсутствуют. Redis и Kafka объявлены как необязательные зависимости.

При реализации платежей запись `payment` и `outbox` должна выполняться в одной транзакции. Отдельная роль publisher публикует событие, дожидается подтверждения RabbitMQ и только затем отмечает запись опубликованной. Повторная доставка всё равно возможна, поэтому consumer должен быть идемпотентным.

Экспоненциальный retry из трёх попыток задан для отправки webhook, а не для всех операций consumer.

## Что нарушает границы

- Импорт FastAPI, Pydantic или SQLAlchemy в `domain/`.
- Импорт реализации репозитория из `infrastructure/` в сценарий `application/`.
- `commit()` внутри репозитория вместо управления транзакцией через Unit of Work.
- Обращение одного модуля к внутренним ORM-моделям другого модуля.
- Размещение бизнес-сущности в `common/` только потому, что она нужна двум модулям.
- Запуск миграций при старте каждой реплики API.

## Проверки при развитии сервиса

Тесты добавляются вместе с реализованным поведением: инварианты домена и сценарии проверяются без внешнего ввода-вывода; репозитории — с тестовой PostgreSQL; HTTP-контракт — через клиент приложения. Шаблон не включает искусственный бизнес-пример и его миграцию.
